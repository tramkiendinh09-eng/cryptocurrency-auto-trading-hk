# 三件待改写的东西 —— 给下一个模型的交接说明

## 背景（一句话）

一个跑在币安 U 本位合约上的多 Agent LLM 交易系统，模拟盘 100 USDT。7 天 5 笔入场、2 笔平仓、**全亏**，而同期池子里的标的普涨（BNB +5.06%、SOL +3.93%、SK海力士 +1.42%、美光 +0.95%）。复盘定位到三个互相咬合的缺陷，下面三件事就是修它们。

## 复盘证据（改写时要能解释掉这些）

**5 笔入场是同一个信号**，无一例外是 Wyckoff `ready` 的 breakout/breakdown + retest confirmed：

| # | 标的 | 方向 | 突破延伸% | 1h量比 | Wyckoff置信 | 主管置信 | 结果 |
|---|---|---|---|---|---|---|---|
| 5 | SOL | 空 | 0.33 | 2.40 | 0.80 | 58 | **-0.50%** |
| 6 | BNB | 多 | 0.22 | 0.74 | 0.78 | 64 | +3.35%（在手） |
| 7 | SK海力士 | 多 | 0.38 | 1.31 | 0.74 | 58 | +2.09%（在手） |
| 8 | 美光 | 多 | 0.38 | 1.28 | 0.74 | 60 | +0.69%（在手） |
| 9 | SOL | 多 | 0.37 | 0.67 | 0.78 | 58 | **-1.48%** |

**亏的两笔都入在区间的错误一端**（按各自 24h 区间算分位）：

| 交易 | 入场价 | 24h 区间 | 分位 |
|---|---|---|---|
| SOL 多 | 105.55 | 99.14~105.88 | **95%**（离最高点 0.3%） |
| SOL 空 | 100.27 | 99.14~105.88 | **17%**（离最低点很近） |

而模型每一次都在自己的理由里写明了问题，却只是缩小仓位而不是放弃：
- 「conservative size because **RSI 81**」
- 「Size cut for RSI 15m/60m **overbought**」
- 「Cut size/confidence: empty memory, 60m EMA still bearish, **15m RSI 71**」

**出场没问题，别动。** 两笔平仓理由都站得住（一笔是 Wyckoff 反转、一笔是跌破失效位），且 SOL 平在 103.99、现价 103.41，出场帮忙避开了又 0.5% 的下跌。平均持仓 209 分钟，落在模型声明的 30m-4h 窗口内。**问题在入场，不在出场。**

**最关键的一条**：这套系统自己的阈值校准报告（`deploy/native/CALIBRATION.md`）早就写过——

> `price_break` 全网格 hit_rate 0.45~0.47，低于 60m 基准 0.5051 —— **分钟涨跌在小时尺度是均值回复**。

均值回复的市场里跑突破检测器，系统性买在局部顶、卖在局部底。这不是运气，是结构。

## 任务一：重写主管提示词的指令段

**文件**：`1-当前提示词构造函数.py`（`_build_supervisor_prompt`），`1b-线上真实提示词样本.txt`（线上真实发出去的完整提示词，16497 字符）

**问题**：指令段 3474 字符，逐词统计——

| 关键词 | 次数 |
|---|---|
| 输出格式/数值口径类（`size_hint`/`JSON`/`must be`/`notional`…） | **35** |
| `risk` | 1（还是 "risk event"，不是风险收益比） |
| `reward` `stop` `edge` `expectancy` `regime` `overbought` `extended` `chase` | **全 0** |

整段在教模型**怎么把 JSON 填对**，没有一句定义**什么样的位置值得进场**。于是模型只能拿 Wyckoff 的 `trade_readiness` 当唯一依据，「多 Agent LLM 决策」退化成一个技术指标的橡皮图章（SKIP 理由清一色 `Wyckoff readiness avoid`）。

**要写进去的（至少）**：
1. **位置纪律** —— 在 4h/24h 区间高分位不追多、低分位不追空。这是挡掉那两笔亏损的直接手段。
2. **风险收益比** —— 现在只要求 `invalidation` 非空，从不要求检查「到失效位的距离 vs 目标空间」是否划算。SOL 那笔从 105.55 进、失效位 104.58，risk 0.9%，reward 未定义。
3. **regime 判断** —— 震荡/均值回复时突破信号必须降级，趋势时才正常采信。
4. **明确的优先级** —— 「宁可错过不可做错」要写成可执行的判据，不能只是口号。
5. **别再用缩小仓位代替放弃** —— 现在模型看见 RSI 81 的反应是 size 减半；正确反应是 SKIP。

**必须保留**：输出仍是严格 JSON，键为 `action, side, confidence, size_hint, leverage_hint, holding_window, invalidation, summary_reason`；`action` 枚举 `OPEN_LONG/OPEN_SHORT/ADD_LONG/ADD_SHORT/REDUCE/CLOSE/HOLD/SKIP`；`size_hint` 是权益比例、敞口 = `account_equity * size_hint * leverage_hint`，需落在 `sizing_constraints.min_size_hint ~ max_size_hint`；`leverage_hint` 是 `min_leverage ~ max_leverage` 的整数。这些口径不能改，改了下游风控和下单会对不上。

**可以删的噪声**（约占提示词 10%）：Wyckoff 检测器的 18 个内部阈值 `config`（570 字符）、`market_api_config` 里的 WebSocket ping 间隔/最大流数/`doc_reference_url`（740 字符）、三个 `*_api_config` 块（312 字符）。模型不需要这些，还会诱导它揣摩检测器内部参数。

## 任务二：给 Wyckoff 加宏观位置过滤

**文件**：`2-wyckoff检测器.py`（599 行，完整文件）

**问题**在第 349 行：

```python
prior_range = fifteen[-5:-1]          # 前 4 根 15 分钟 K = 只有 1 小时
range_high = max(_high(item) for item in prior_range)
range_low  = min(_low(item)  for item in prior_range)
```

所谓「confirmed breakout」= **价格超过前一小时的最高点，且超出 ≤0.9%**（`maxReadyExtensionPct`）。这个检测器**完全不知道自己在日内区间的什么位置**。SOL 那笔突破延伸只有 0.37%（看着很健康），但在 24h 区间的 95 分位。

**要做的**：保留 1 小时突破的敏感度，**增加**一个宏观位置维度——比如把当前价在 4h / 24h 区间的分位算出来，作为新字段进 `feature_snapshot`，高分位否决做多、低分位否决做空。阈值不要拍脑袋定，见下面「怎么验证」。

**必须保留**：现有输出字段名（`status` `phase` `entry_bias` `trigger` `trade_readiness` `confidence` `no_trade_reason` `trap_risk` `breakout_extension_pct` `range_high` `range_low` `invalidation` …）下游 `trigger_policy.py` 和提示词都在读，改名会静默断链。新增字段可以自由加。

**怎么验证**：仓库里有现成回测框架 `python-worker/trade_runtime/calibration/`（history / replay / sweep / cli，30 个单测），判定复用生产的 `evaluate_trigger_policy`，不复制阈值比较逻辑。**分位阈值应该跑 sweep 定，不要猜。** 注意两个已知坑：`openInterestHist` 只留 30 天；sweep 必须隔离被测维度，否则其它维度在同样 K 线上触发会让不同取值得到相同 dispatch 数。

## 任务三：把方法论落进模板表，别再堆在代码兜底串里

**文件**：`3-模板绑定解析器.py`、`3b-模板如何接入主管.txt`

**问题**：`prompt_template` 和 `trade_prompt_binding` **都是 0 行**，而 808/808 次决策 `prompt_source = inline`。整套模板体系——前端两个管理页、后端控制器、`prompt_binding_resolver.py`、配套测试——**建好了却从没往里放过一条数据**，实际跑的是代码里那个只讲格式的兜底串。

**表结构** `prompt_template`：

```
id bigint | code varchar(255) | name varchar(255) | content text
variables varchar(255) | version int | is_active int | is_default int
remark text | create_by/create_time/update_by/update_time
```

**要做的**：把任务一写出来的方法论作为一条模板落进 `prompt_template`，并在 `trade_prompt_binding` 里绑到 supervisor。好处是以后调策略改一行数据即可，不用改代码、不用重新部署 worker，还能 A/B 和版本回滚。

**注意**：接入后 `decision_run.prompt_source` 应该从 `inline` 变成模板来源，`resolved_template_code` 有值——这是验证是否真正生效的判据。**只看「调用成功」不够**，这个系统里已经出现过多次「参数被丢掉但调用照样成功」的情况（`reasoning_effort` 曾经无路径下发、`entry_trace_id` 曾被 LangGraph 静默丢弃）。

## 建议顺序

**任务二 → 任务一 → 任务三**。

先做位置过滤：它有数据支撑、能用回测量化、风险可控。再动提示词：影响面大且难以量化，如果先改提示词，就没法区分是提示词起效了还是市场变了。

## 一个必须知道的风险

仓位下界当前是 `minPositionRatio = 0.40`，6 倍杠杆下单笔名义 240 USDT（账户 100 USDT）。**在入场质量修好之前，这个仓位会把同样的错误放大 8 倍。** 建议先调回 0.15 左右，等回测验证完再放回去。

配置位置：`trade_runtime_config.runtime_flags_json`。相关键：`minPositionRatio`、`maxLeverage`(12)、`baselinePolicy`、`positionRiskWatcher`、`llmBudgetPolicy`。
